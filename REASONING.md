CafePoints is a full-stack loyalty points platform designed for a cafe/restaurant environment.

The application allows staff/admin users to manage loyalty members, record purchases, award points, manage rewards, and redeem points. The platform also implements tier progression, point expiration, and notification/outbox functionality.

The project is divided into:

React + Vite frontend
Node.js + Express backend
MongoDB database
Mongoose for database modeling
JWT for authentication
bcrypt for password hashing

The main objective was to keep the system modular while making the loyalty rules easy to extend and test.

2. Architecture Decision

The application uses a separated frontend/backend architecture.

                    ┌─────────────────────┐
                    │     React/Vite      │
                    │      Frontend       │
                    └──────────┬──────────┘
                               │
                         REST API / HTTP
                               │
                    ┌──────────▼──────────┐
                    │   Node + Express    │
                    │      Backend        │
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
                    │       MongoDB       │
                    │     + Mongoose      │
                    └─────────────────────┘

This separation allows the frontend to remain independent of the backend implementation and makes the API reusable for other clients.

3. Data Modeling

The backend uses separate models for different responsibilities.

User

The User model stores authentication-related information.

It contains information such as:

name
email
password hash
role

Passwords are hashed with bcrypt before storage.

Member

The Member model represents a loyalty customer.

Important information includes:

customer/member identifier
customer information
current points
lifetime points
current loyalty tier

Lifetime points and available points are intentionally treated as separate concepts.

Reasoning

Available points represent what a customer can currently spend.

Lifetime points represent the customer's historical loyalty progress.

Therefore, expiration or redemption should reduce available points without incorrectly reducing lifetime progress.

Transaction

Transactions provide an audit trail for loyalty activity.

Examples include:

purchase
points earned
points redeemed
points expired

Keeping transactions separately from the member balance makes the system easier to audit and debug.

Reward

The Reward model stores rewards that can be redeemed using loyalty points.

A reward contains information such as:

reward name
description
points cost
availability/status
PointLot

Point lots are used to track individual groups of earned points.

This is particularly useful for the 90-day expiration requirement because points can be associated with their own expiration time.

Instead of simply storing one large points balance, the system can determine which earned points have become stale.

OutboxEvent

The outbox model stores events generated by important business operations.

For this project, tier changes can generate notification events.

This makes notification generation observable and prevents notification behavior from being tightly coupled to the frontend.

4. Authentication Reasoning

JWT-based authentication was selected because the application exposes REST APIs and needs protected staff/admin functionality.

The general flow is:

Login
  ↓
Validate credentials
  ↓
Generate JWT
  ↓
Client stores authenticated session
  ↓
Protected API request
  ↓
Authentication middleware validates JWT

Passwords are hashed using bcrypt.

Authentication and authorization are separated:

Authentication determines who the user is.
Authorization determines what role that user is allowed to access.
5. Loyalty Tier Design

The loyalty tier calculation is centralized instead of being duplicated across multiple routes.

This is important because tier rules are business rules and should have a single source of truth.

The tier system includes:

Bronze
Silver
Gold
Platinum

The Platinum requirement is:

Lifetime points >= 5000

The Platinum earning rate is:

0.3 points per ₹1

The tier is determined from lifetime points rather than the current spendable balance.

6. Why Lifetime Points Are Used for Tiers

A customer may lose points because of redemption or expiration.

If the tier were calculated using only available points, a loyal customer could unexpectedly lose their tier after redeeming rewards.

Using lifetime points avoids this problem.

Example:

Customer earns 5000 lifetime points
        ↓
Customer reaches Platinum
        ↓
Customer redeems 1000 points
        ↓
Available points = 4000
Lifetime points = 5000
        ↓
Customer remains Platinum

This matches the intended concept of a loyalty progression system.

7. Platinum Tier — T3

The Platinum tier was added as an extension to the existing tier system.

The important compatibility requirement was that existing members should continue operating normally unless they qualify for Platinum.

The calculation therefore follows a descending threshold approach:

if lifetime points >= 5000
    Platinum
else if eligible for Gold
    Gold
else if eligible for Silver
    Silver
else
    Bronze

This keeps the existing tiers intact while adding Platinum above them.

8. Point Expiration — T2

The requirement specifies that points expire after 90 days.

The expiration period is therefore represented as:

90 days

When points are earned, their expiration information can be tracked separately.

The system can later identify point lots whose expiration date has passed.

9. Why Point Lots Are Used

A single member balance is insufficient for accurate expiration.

Consider:

January:
Earn 100 points

February:
Earn 200 points

If only the total balance of 300 is stored, the system cannot determine which points should expire first.

Using point lots allows the system to preserve the origin and expiration information for each group of earned points.

This also provides a foundation for FIFO-style expiration.

10. Expiration Processing

The expiration process is exposed through:

POST /clock

The endpoint provides a deterministic way to trigger the expiration logic during testing.

The general process is:

POST /clock
      ↓
Find expired point lots
      ↓
Calculate points that should expire
      ↓
Reduce available balance
      ↓
Create expiration transaction
      ↓
Mark expired points as processed

Lifetime points are not reduced because expiration changes the customer's spendable balance rather than their historical loyalty achievement.

11. Why /clock Is Used

A real production application could use a scheduled worker or cron system.

However, relying only on real time makes automated evaluation difficult.

For example, an evaluator should not have to wait 90 days to verify expiration behavior.

The /clock endpoint makes the expiration process explicitly triggerable and therefore testable.

This is especially useful for deterministic integration testing.

12. Notification Service — T1

Tier changes are treated as business events.

When a member moves from one tier to another, the application can generate a notification event.

The general flow is:

Purchase
   ↓
Points added
   ↓
Lifetime points updated
   ↓
Tier recalculated
   ↓
Old tier != new tier
   ↓
Notification service
   ↓
Outbox event

The notification service is separated from the core purchase logic to keep responsibilities clear.

13. Why an Outbox Is Used

Directly sending a notification inside the purchase operation creates tighter coupling.

Instead, the system records an event.

For example:

TIER_CHANGED

The event can contain information about:

member
previous tier
new tier
event time

The outbox can then be inspected using:

GET /outbox

This gives the evaluator a visible representation of the notification event.

14. Tier Change Detection

The system needs to distinguish between:

Member remains in same tier

and:

Member enters a new tier

The comparison is therefore conceptually:

oldTier !== newTier

Only an actual tier transition should generate a tier-change notification.

This prevents duplicate notifications when a customer makes additional purchases while remaining in the same tier.

15. Purchase Flow

The purchase operation is the central loyalty operation.

The intended process is:

Select member
       ↓
Enter purchase amount
       ↓
Read current tier
       ↓
Determine earning rate
       ↓
Calculate points
       ↓
Create point lot
       ↓
Update available points
       ↓
Update lifetime points
       ↓
Recalculate tier
       ↓
Create transaction
       ↓
Generate tier event if required

The tier configuration therefore determines the earning rate rather than hardcoding different calculations in every route.

16. Redemption Flow

The redemption process verifies that the member has enough available points before allowing the redemption.

Conceptually:

Select reward
       ↓
Read reward point cost
       ↓
Read member available points
       ↓
Check sufficient balance
       ↓
Deduct points
       ↓
Create redemption transaction

A member's lifetime points should not decrease when they redeem a reward.

17. Error Handling

The backend validates important business conditions before modifying data.

Examples include:

invalid authentication
missing member
invalid purchase amount
insufficient points
invalid reward
unauthorized access

This prevents invalid requests from silently modifying the database.

18. Frontend Reasoning

React was used for the frontend because the application contains multiple interactive views and requires state updates after operations.

The frontend contains pages/components for functionality such as:

Login
Member List
Counter
Customer Portal
Admin Dashboard
QR Scanner

Reusable layout and authentication components help avoid duplicating application-level logic.

19. API Communication

The frontend communicates with the Express backend through a centralized API layer.

This makes API calls easier to maintain and reduces duplicated HTTP configuration.

The backend remains responsible for business validation.

The frontend should therefore not be treated as a trusted source for loyalty calculations.

20. Environment Variables

Sensitive configuration is intentionally kept outside source code.

Important environment variables include:

The real .env file should remain local and should never be committed to a public GitHub repository.

21. Debugging and Fixes
Backend Environment Issue

During development, the backend reported:

MONGO_URI is not set in .env

The issue was investigated as an environment configuration problem.

The backend was configured to read the expected environment variable, and the environment file location/name was checked.

The important variable is:

MONGO_URI

The environment file must also be named correctly as:

.env

rather than:

.env.txt
Frontend Counter Issue

The Counter page initially had an issue related to missing/incorrect state/function references.

The component was reviewed and corrected so that the purchase/points flow could use the required state and loyalty configuration.

The tier configuration was also extended to include Platinum.

22. Testing Strategy

Testing was focused on the business rules introduced by the requirements.

Test 1 — Existing Tier

Create a member below the Platinum threshold.

Expected:

Tier remains existing tier
Test 2 — Platinum Upgrade

Create or use a member whose lifetime points are close to 5000.

Perform a purchase that causes:

lifetime points >= 5000

Expected:

Tier changes to Platinum
Test 3 — Platinum Earning Rate

After Platinum is reached, make another purchase.

Expected:

Points earned = purchase amount × 0.3

subject to the application's point calculation behavior.

Test 4 — Point Expiration

Create earned points with an expiration date.

Move/test the clock beyond the expiration date.

Execute:

POST /clock

Expected:

Available points decrease
Expiration transaction/event is recorded
Lifetime points remain unchanged
Test 5 — Tier Notification

Cause a member to cross a tier threshold.

Then query:

GET /outbox

Expected:

A tier-change event is present
Test 6 — Redemption

Select a reward and redeem it using sufficient points.

Expected:

Available points decrease
Redemption transaction is created

If the member has insufficient points, redemption should be rejected.

23. Backward Compatibility

The new features were implemented as extensions to the existing loyalty system.

The main compatibility principles are:

Existing tier rules remain available.
Platinum is added above the previous tiers.
Lifetime points continue representing historical earning.
Expiration affects available points rather than lifetime points.
Existing members are not artificially reset.
Tier evaluation happens using the same centralized calculation.

25. Security Considerations

The following security practices were considered:

Passwords are hashed using bcrypt.
JWT is used for authentication.
Protected routes use authentication middleware.
Role-based access is used where required.
Database credentials are stored in environment variables.
Real .env files should not be committed.
.env.example contains placeholders instead of secrets.

For production deployment, additional security measures such as stronger secret management, rate limiting, HTTPS, validation, monitoring, and secure cookie configuration should also be considered.

26. Final Engineering Reasoning

The implementation prioritizes three important properties:

Correctness

Loyalty points, tiers, expiration, and redemption are handled as explicit business rules.

Testability

The /clock endpoint and /outbox endpoint make the new requirements observable and easier to evaluate.

Extensibility

Tier rules, notification behavior, point tracking, and database models are separated so additional loyalty features can be added without rewriting the entire application.
